## 一、八秒不算慢，但不对劲

站点不到三十篇文章，`hugo --gc --minify` 本地要跑八秒出头。绝对数字不吓人，可**同样的仓库上周还是两秒**，中间只加了两三个功能。

> 变慢本身不可怕，可怕的是不知道从哪一版开始慢的。

先按最笨的办法：`git log` 翻最近十个提交，逐个 checkout 构建计时。

| 提交 | 构建 | 怀疑点 |
|---|---|---|
| 加进度条 | 2.1s | 无关 |
| 加搜索权重 | 2.2s | 无关 |
| 归档页本地化 | **7.9s** | ✓ 就是它 |
| 之后两个 | 8.0s | 沿用 |

*元凶一分钟就锁定了。*真正花时间的是后面——为什么一个归档页会贵六秒。

## 二、三个没用的尝试

按直觉先后试过：

1. **以为是图片**：把 `resources` 清了重跑，没变化
2. **以为是 `--gc`**：去掉参数，8.0 → 7.9，不是
3. **以为是模板嵌套**：把归档模板简化到只剩一个 `<ul>`，还是 7.8

- [x] 清缓存
- [x] 去 --gc
- [x] 简化模板
- [ ] ~~准备换生成器~~（幸好没动手）

第三个试完我才想到：**模板里那行分类查询，是不是每次循环都在跑**。

## 三、那行代码

归档页要按年月分组，原写法大概是这样：

```go
{{ range .Site.RegularPages }}
  {{ $y := .Date.Format "2006" }}
  {{ $posts := where (where .Site.RegularPages "Section" "posts") "Date" ">" ... }}
  {{ range $posts }}…{{ end }}
{{ end }}
```

外层 `range` 有 N 篇，里层 `where` 就**对全站页面筛了 N 次**。文章少的时候看不出来，加上多语言三倍页面数，复杂度一下就显出来了。

改法一点都不聪明：把筛选**提到循环外，只做一次**。

```go
{{ $all := where .Site.RegularPages "Section" "posts" }}
{{ $groups := $all.GroupByDate "2006-01" }}
{{ range $groups }}…{{ end }}
```

`GroupByDate` 是 Hugo 自带的，之前居然没想起来用。

## 四、数字

| 指标 | 改前 | 改后 |
|---|---|---|
| 本地构建 | 8.0s | **2.1s** |
| 模板执行 | 6.7s | 0.8s |
| CI 总时长 | 41s | 33s |
| 代码行数 | 22 | 9 |

> 删掉十三行，快了六秒。**这大概是本周性价比最高的一次提交。**

## 五、为什么值得记

因为前三个尝试全是错的，而且都很「像」对的。清缓存、去参数、简化模板——每一步都有道理，每一步都测了，每一步都没用。

真正有用的是**先量后猜**：把每个提交的构建时间列成表，慢的那一版自己就跳出来了。要是直接凭经验去优化图片，大概现在还在给根本没变的图片做 WebP。

- **先定位，再动手**
- 别优化你没量过的东西
- 框架自带函数先查一遍，别自己写循环
- ~~八秒也能忍~~ 不能忍

## 六、收尾

现在 `Total in 2.1s`，跟加功能之前一样。归档页还是那个归档页，年月分组、三语、RSS 入口都在，只是不再把同一份页面列表数三十遍。

**代码变少，站点变快，没有新增任何依赖。** 这种日子值得写下来。

[^1]: `hugo --templateMetrics` 能直接看到每个模板的累计耗时，这次是事后才知道的，下次先开它。
