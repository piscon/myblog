## 一、全绿，但链接是死的

上线后第三天偶然点了一下文章页底部的**「在 GitHub 上改进本文」**，跳过去 404。顺手点了另外两篇，一样。

奇怪的是：

| 检查 | 结果 |
|---|---|
| 本地 `hugo --gc --minify` | ✅ |
| CI build-check | ✅ |
| feature-check 26 项 | ✅ |
| Netlify 部署日志 | ✅ 全绿 |
| 那个链接 | **404** |

> 所有自动检查都在验证「页面能不能生成」，没一个在验证「生成出来的地址对不对」。

## 二、一行 main

站点层的 `editPost` 配置长这样（简化）：

```toml
[params.editPost]
  URL = "https://github.com/piscon/myblog/blob/master"
  appendFilePath = true
```

出事的版本里那个 `master` 写成了 **`main`**。仓库默认分支一直是 `master`，GitHub 上 `blob/main/...` 自然不存在。

**错的是一个字母串，不是逻辑。** Hugo 不校验这个 URL，模板只负责拼字符串，构建当然全绿。

- [x] 拼出来的路径格式对
- [x] 文件存在
- [ ] **分支名没人核过**
- [ ] 也没人点过成品链接

*写配置的时候我大概顺手敲了更常见的那个词。*

## 三、为什么没被测出来

复盘时最在意的不是「写错」，是「为什么错得这么安静」。

1. **它是纯数据**，不是代码，静态检查无从下手
2. **feature-check 断言的是 DOM 结构**（有没有 `a.edit`、class 对不对），不跟外域地址
3. 本地点过吗？**没有**。开发时都在看排版
4. Netlify 只管构建，不管你链到哪儿

| 层 | 能发现吗 | 原因 |
|---|---|---|
| Hugo 模板 | 不能 | 只做字符串拼接 |
| 构建校验 | 不能 | 不解析 URL |
| feature-check | 不能 | 断言选择器，不断言外链 |
| 人工点一下 | **能** | 但三天后才点 |

> 这类 bug 的正式名字大概叫「**没人负责的那一格**」。

## 四、补的那一格

修法本身一秒：改回 `master`。但补防线花了一点心思。

给 `feature-check.sh` 加了一条断言，直接 grep 构建产物里的编辑链接，**校验分支段必须等于仓库默认分支**：

```bash
check "editPost 分支与默认分支一致" \
  "grep -q '/blob/$(git symbolic-ref --short refs/remotes/origin/HEAD | sed 's|origin/||')/' '$PAGE'"
```

再加一条注释写在 `hugo.toml` 旁边：

```toml
# 分支必须与仓库默认分支一致（master）——曾误写 main 致全站死链
```

| 补法 | 防什么 |
|---|---|
| 断言分支段 | 以后再写错，CI 直接红 |
| 配置旁注释 | 人改之前先看见 |
| 复盘写进文档 | 下次别再靠「顺手点一下」 |

- [x] 改回 master
- [x] 加断言（现在 27 项）
- [x] 加注释
- [ ] 顺便把其它写死的域名也扫一遍（记了 TODO）

## 五、比修 bug 更值得留的

这次之后我改了个习惯：**构建绿了不算完，随手点一个成品链接**。成本三秒，刚好覆盖所有「数据写错但格式合法」的坑。

还有一个更一般的结论：**自动检查擅长验证结构，不擅长验证事实**。结构错了会炸，事实错了（分支名、域名、日期、ID）会安静地错很久。所以断言里要尽量混几条「事实型」的，哪怕只是 grep 一个字符串。

> 那行注释现在还躺在配置文件里。它不执行，但每次有人想改那个 URL，都会先读到「曾误写 main 致全站死链」。

**代码管行为，注释管记性。** 这次两样都用上了。
