这个博客是三语的（简体中文 / 日本語 / English）。写完中文 push 上去，日文和英文版几分钟内自动生成、自动部署上线——本文完整介绍这条流水线的最终形态。

## 整体架构

```
写完中文文章 push
  → GitHub Actions（translate-content）
    → 经 AI Gateway 调 Cloudflare Workers AI
    → 产物过 Hugo 构建校验（防坏 front matter 打挂部署）
    → bot 提交回写 git
      → Netlify 自动部署，日/英文版上线
```

四条设计原则：

- **产物进 git**：译文可审阅、可回滚、可人工接手，Netlify 构建拿到的永远是成品 Markdown
- **访客侧完全静态**：API 凭据只存在于 GitHub Actions，前端零密钥、零额外请求、零第三方脚本
- **所有请求走 AI Gateway**：每条请求的 token、美元成本、耗时都有日志可查；同内容重跑命中缓存，零消耗
- **部分失败不拖垮整体**：某语言翻译失败不影响另一语言上线

## 模型与调用方式

模型用 `@cf/qwen/qwen3-30b-a3b-fp8`（免费计划可用，MoE 架构激活参数仅 3B，计费档位最低），并关闭思考模式——翻译任务不需要推理，省额度也更稳定。

每次翻译拆成两段调用：

| 调用 | 内容 | 输出约束 |
|---|---|---|
| 字段 | 标题 / 摘要 / 分类 / 标签 / 封面文字 | JSON Schema 强约束，格式非法直接被 API 拦下 |
| 正文 | Markdown 全文 | 纯文本输出，Markdown 结构保真 |

正文翻译有一条**结构 QA 门**：译文与原文比对行内链接、标题、代码围栏的数量，发现缩水先按原文 URL 清单机械自愈（把被打散的链接还原成 `[文字](URL)`），自愈不成再重译。配合输出截断守卫（到 max_tokens 上限自动加预算重试）、180 秒超时和 429/5xx 指数退避，单次 run 的失败面很小。

## 增量：双 hash

每个译文文件的 front matter 带两个标记：

```toml
source_hash = '…'        # 正文的 sha256（混入提示词版本号与模型名）
source_fields_hash = '…' # 字段集的 sha256
```

- 中文**正文**改了 → 只重译正文，字段沿用原译文
- 只改了**摘要/标签** → 只重译字段，正文分文不花
- 换模型或升级提示词 → 版本号变化 → 全量重译一遍
- 什么都不变 → 0 次 API 调用（每周日 03:17 的定时对账就是这样全量扫描兜底的）

## SEO 摘要也归它管

中文文章没写摘要（CMS 里留空）也没关系：流水线会生成一段 70-160 字的摘要写回 front matter，三语字段翻译以它为源——**中日英三语摘要永远同源**。之后你在 CMS 里改写摘要保存，三语自动跟进。

## 人工永远有一票

- CMS 译文条目勾**「锁定译文」**→ 这份译文视同人工稿件：永不覆盖、永不删除，中文原文更新也不再同步
- CMS 中文条目勾**「不翻译」**→ 本篇退出流水线
- 校对过的机翻，只要中文源对应部分不动就不会被重译（CMS 保存不会破坏 hash 标记）
- 生命周期同步：中文删除 → 译文自动清理；中文转草稿 → 译文自动下架

## 成本

免费计划每天 10,000 neurons。实测：一篇全文三语翻译约 100 neurons；只改摘要约 5 neurons；日常增量远踩不到上限。AI Gateway 日志里每条请求的 token、美元成本、耗时都可直接查询。
