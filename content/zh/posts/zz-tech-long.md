## 1. 问题域

一个静态博客要同时维护三种语言，最直觉的做法是给每篇文章写三份 Markdown。但很快会遇到三个问题：**重复劳动**、**版本漂移**、**结构不一致**。中文改了一个链接，日文和英文版往往忘记同步；某个语言用了错误的标题层级，只有发布后才会被发现[^1]。

> 工程上更可靠的思路是：把「可译的自然语言」与「不可译的机器语法」分开，让机器只处理前者，后者由程序拼装。

本文讨论的流水线建立在三个约束之上：

1. 内容必须落盘为普通 Markdown，便于审阅、回滚与人工接手
2. 翻译过程不得改写 URL、代码块、列表标记与链接目标
3. 任意一步失败时，已发布的内容保持原样，不允许半损坏页面上线

## 2. 内容建模

### 2.1 目录与语言

Hugo 的多语言模式按 `contentDir` 划分目录，每篇文章在三个目录下使用**同名文件**：

| 语言 | 目录 | 文件名 | 说明 |
|---|---|---|---|
| 简体中文 | `content/zh/posts` | `article.md` | 唯一真源 |
| 日本語 | `content/ja/posts` | `article.md` | 生成物 |
| English | `content/en/posts` | `article.md` | 生成物 |

同名的好处是 `translation_list` 与 `hreflang` 可以直接按路径对齐，不需要额外的映射表。代价是**重命名必须同步三个目录**，并把旧路径写进 `aliases` 字段生成跳转页。

### 2.2 front matter 字段

字段分两类。第一类是读者可见、需要翻译的：

- `title`、`description`
- `categories`、`tags`
- `cover.alt`、`cover.caption`

第二类是机器消费、必须原样保留的：

- `date`、`draft`、`weight`
- `aliases`、`searchHidden`、`robotsNoIndex`
- `source_hash`、`source_fields_hash`

增量翻译依赖两个哈希：正文哈希与字段哈希**互不连坐**。改摘要只重译字段，改正文只重译正文。这一点在频繁修改错别字时尤为重要，能省下大量无谓调用。

## 3. 翻译流水线

### 3.1 保护 pass

Markdown 不是纯文本，它混合了两种语言：人读的散文与机器读的标记。若把整篇交给模型，实测会出现如下损伤：

```markdown
原文：1. *感谢 [Hugo](https://gohugo.io) 提供代码支持*
损伤：[1. *Hugo](https://gohugo.io)にコードのサポートを感謝します*
```

注意链接数量、标题层级、围栏计数**全部守恒**，因此基于计数的检查会静默放行。修复方式不是继续加提示词，而是让模型根本看不到语法：

```python
def translate(body: str, lang: str) -> str:
    protected, tokens = protect(body)   # «0» «1» …
    raw = model(protected, lang)        # 模型只见散文
    assert all(t.count == 1 for t in tokens)
    return restore(raw, tokens)
```

被保护的原子包括：

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 围栏代码块 | ```` ```python ```` | 整块替换，不进模型 |
| 链接目标 | `](https://…)` | URL 与括号保护 |
| 骨架标记 | `## `、`1. `、`\|` | 成对保护，须贴行首/行尾 |
| 行内代码 | `` `token` `` | 原样保留 |
| 脚注与复选框 | `[^1]`、`[x]` | 原子化 |

### 3.2 分块与节流

长序列的编号标记会被模型稳定地吞掉。经验区间是：**19 个标记以内可靠，64 个以上必现丢失**。于是按行切单元、贪心合并到每块约 20 个标记，编号每块从 0 开始。

请求层还要统一节流。网关设置经核实为 100 请求 / 60 秒滑动窗口，但实测 61 次/分钟即触发持续 429，且只有缓存命中能放行；关闭该开关后问题消失。因此客户端仍保留 2 秒间隔（峰值 30 次/分钟），给上游留足余量。

### 3.3 完整性门与降级

译后检查三件事：

- [x] 每个标记恰好出现一次
- [x] 骨架标记仍在行首或行尾
- [x] 还原后的结构计数守恒

任何一项失败即重试；连续失败则把该块**二分重译**，且只在两半各自可独立还原的边界切分，避免劈开围栏或表格。正常路径零额外开销，失败路径多花几次调用换取成功率。

### 3.4 失败语义

流水线对失败的定义刻意保守：**不写新文件，旧译文原地保留**。这与常见的「部分成功即提交」并不矛盾——成功的部分照常写入，失败的语言维持上一版内容。线上读者看到的可能是稍旧的译文，而不是结构损坏的页面。

三种典型失败路径：

1. 模型输出被 `max_tokens` 截断 → 加预算重试
2. 完整性门拦下 → 整块重试，再失败则二分
3. 上游返回 429/5xx → 指数退避或等满限流窗口

第 2 类最值得展开。假设某块包含二十个标记，模型把其中一对 `**` 吞了，门会报「缺失 2 个」；重试时提醒模型保留标记，若仍失败，则把该块按行切成两半分别调用。两半各约十个标记，丢原子的概率显著下降。实测中一次典型的降级是 21 行切成 1 行 + 20 行，随后两半都通过。

### 3.5 关于缓存

网关提供 7 天响应缓存：同样的 prompt 重放不消耗 neuron，也不转发上游。这对**重跑**特别有用——某次 run 失败后，已经成功的块再次请求会直接命中缓存，只有失败的块重新计费。

但缓存也带来一个容易误判的现象：当上游或网关进入限流状态时，只有缓存命中的请求能返回 200，其余一律 429。若只看「有成功日志」就以为配额正常，会得出完全错误的结论。判断配额是否健康，必须看**非缓存请求**的返回码。

一个相关的细节是：缓存键由完整请求体决定，因此提示词版本号变化会使所有历史缓存失效。这也是为什么升级提示词后，下一次全量重译的费用会明显偏高，属于预期行为而非故障。

### 3.6 字段调用与正文调用

两类调用的形状不同，不宜混为一谈：

| 维度 | 字段调用 | 正文调用 |
|---|---|---|
| 输入 | 标题、摘要、标签等短文本 | 分块后的正文 |
| 输出约束 | JSON Schema 强约束 | 纯文本 |
| 常见故障 | 模型拒绝 schema | 标记丢失、截断 |
| 重试策略 | 降级为纯解析 | 二分降级 |

字段调用使用 `response_format: json_schema` 后，格式非法会在 API 层被拦下，几乎不需要额外的结构检查。但个别模型并不稳定支持该参数，报「JSON Mode couldn't be met」时脚本会自动降级为普通 JSON 解析，并在本次会话内记住这个语言不再尝试 schema。正文则相反：Markdown 塞进 JSON 会被模型打散链接语法，因此必须走纯文本。

## 4. 验证策略

离线自测不消耗任何 API 调用，覆盖四类断言：

1. 全语料恒等往返：保护与还原互逆
2. 分段恒等往返：分块不改变空行结构
3. 旧事故等价攻击：标记被删除、重复、位移、越界时门必须拦下
4. 速率预算：两篇中长文的调用数与峰值速率上界

渲染层还需比对三语 HTML 的 `table`、`tr`、`td`、`ol`、`ul`、`li`、`pre`、`code`、`del`、`sup`、`input` 计数，确保结构完全一致。编译成功只证明文件能构建，不等于页面正确。

### 4.1 构建期校验

译文回写 git 之前，CI 会先跑一次 `hugo --gc --minify`。这一步的目的不是检查译文质量，而是拦截**坏掉的 front matter**：TOML 里少一个引号、数组括号不配对，都会让整个站点的构建失败。把这道门放在提交前，可以避免把打挂部署的内容写进仓库。

一个容易忽略的点是 `aliases`。旧路径在多语言模式下不能带语言前缀，Hugo 会自动按语言落地；手写前缀反而会生成错误的跳转页。类似这样的约定，与其写进文档等人读，不如放进离线断言里，让脚本每次都替人检查一遍。

### 4.2 主题升级的耦合点

主题以 submodule 形式引入，每周都有上游更新。站点层只覆盖少量必要的模板，其余功能尽量通过 front matter 字段与扩展点表达。覆盖越多，每周合并 PR 时出现冲突的概率越高。

因此需要一张耦合点清单：哪些选择器、哪些钩子、哪些 partial 名是站点层依赖的。每次升级前后各跑一次断言，失败时直接给出 DOM 快照，方便定位是哪个上游改动碰到了假设。这份清单本质上是一份**可执行的接口契约**，比注释可靠得多。

## 5. 职责边界

| 层 | 职责 | 不该做什么 |
|---|---|---|
| 内容管理 | 输入普通 Markdown | 不承载业务逻辑 |
| 站点模板 | 渲染与扩展点 | 不修改上游主题本体 |
| 翻译脚本 | 结构保真 | 不判断译文好坏 |
| CI | 触发与回写 | 不轮询运行状态 |

把功能逻辑放在**稳定且全表达**的层，是这套设计里最值得复用的一条原则。主题每周更新，模板覆盖越多，合并冲突越频繁；因此能用 front matter 字段表达的，就不要覆盖模板。

## 6. 小结

- 可靠性来自「模型接触不到语法」，而不是「模型听话」
- 失败时旧内容原地保留，线上永不出现损坏页面
- 提示词保持极简，复杂规则全部下沉到程序
- 每次结构变更都要有离线断言兜底
