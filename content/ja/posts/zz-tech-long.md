## 1. 問題領域

静的なブログを3つの言語で同時に運用する場合、最も直感的な方法は各記事を3つのMarkdownファイルで書くことである。しかしすぐに3つの問題に直面する。**繰り返し作業**、**バージョンのずれ**、**構造の不一致**。中国語でリンクを変更しても、日本語版や英語版はしばしば同期されない。ある言語で誤った見出しレベルを使用した場合、公開後に初めて気付くこともある[^1]。

> エンジニアリング的により信頼性の高いアプローチは、「翻訳可能な自然言語」と「翻訳不可能なマシン構文」を分離することである。マシンは前者のみを処理し、後者はプログラムによって組み立てられる。

本書で議論するパイプラインは次の3つの制約に基づいている。

1. コンテンツは通常のMarkdownとしてディスクに保存される必要がある。これにより、レビュー、ロールバック、人間による引き継ぎが容易になる。
2. 翻訳プロセスではURL、コードブロック、リストの記号、リンクの先を変更してはならない。
3. どのステップでも失敗した場合、すでに公開されたコンテンツは元の状態を保ち、部分的に破損したページが公開されることはない。

## 2. コンテンツモデル

### 2.1 ディレクトリと言語

Hugoの多言語モードは`contentDir`ディレクトリで言語を区別し、各記事は3つのディレクトリで**同じ名前のファイル**を使用する。
| 言語 | ディレクトリ | ファイル名 | 説明  |
| --- | --- | --- | --- |
| 簡体中国語 | `content/zh/posts` | `article.md` | 唯一の真の源  |
| 日本語 | `content/ja/posts` | `article.md` | 生成物  |
| イギリス語 | `content/en/posts` | `article.md` | 生成物  |
同名の利点は `translation_list` と `hreflang` が直接パスで対応付けられ、追加のマッピングテーブルが不要になることです。代償は ** の名前変更が3つのディレクトリ ** で同時に進められ、古いパスが `aliases` フィールドに記載され、リダイレクトページが生成される必要があります。

### 2.2 front matter フィールド

フィールドは2種類に分けられます。1つ目は読者に表示され、翻訳が必要なものです：

- `title`、`description`
- `categories`、`tags`
- `cover.alt`、`cover.caption`

第二の種類は機械的に消費されるもので、必ずそのまま保持する必要があります：

- `date`、`draft`、`weight`
- `aliases`、`searchHidden`、`robotsNoIndex`
- `source_hash`、`source_fields_hash`

インクリメンタル翻訳は2つのハッシュに依存しています：本文ハッシュとフィールドハッシュ**はお互いに影響しない**。要約を変更するときはフィールドのみを再翻訳し、本文を変更するときは本文のみを再翻訳します。この点は頻繁に誤字を修正する際に特に重要で、無駄な呼び出しを大幅に節約できます。

## 3. 翻訳パイプライン

### 3.1 保護パス

Markdownは純粋なテキストではありません。人間が読む文章と機械が読むタグが混在しています。全文をモデルに渡すと、実際のテストで以下の損傷が発生する可能性があります。

```markdown
原文：1. *感谢 [Hugo](https://gohugo.io) 提供代码支持*
损伤：[1. *Hugo](https://gohugo.io)にコードのサポートを感謝します*
```
注意リンク数、タイトルレベル、囲みの数**はすべて保存される**ため、カウントに基づくチェックは黙って許可される。修正方法は引き続きヒントを追加することではなく、モデルが文法をまったく見ないようにすることである：

```python
def translate(body: str, lang: str) -> str:
    protected, tokens = protect(body)   # «0» «1» …
    raw = model(protected, lang)        # 模型只见散文
    assert all(t.count == 1 for t in tokens)
    return restore(raw, tokens)
```

保護されたアトムには以下が含まれる：

| タイプ | 例 | 処理方法 |
|---|---|---|
| コードブロック | ```` ```python ```` | 整塊置換、モデルに入らない  |
| リンクのターゲット | `](https://…)` | URL と括弧の保護  |
| スケルトンマーカー | `## `、`1. `、`\|` | はペアで保護され、行頭または行末に貼り付ける必要があります  |
| 行内コード | `` `token` `` | はそのまま残します  |
| 脚注とチェックボックス | `[^1]`、`[x]` | 原子化  |

### 3.2 ブロック化とフロー制限
長期間の番号マーカーはモデルによって安定して破棄される。経験的な範囲は、**19 マーカー以内であれば信頼性が高く、64 マーカー以上になると必ず失われる**。そのため、行単位でセグメントに分割し、貪欲に20マーカー程度になるまで結合し、各ブロックの番号は0から始める。

リクエスト層では統一されたリミット処理が必要である。ゲートウェイの設定では100リクエスト/60秒のスラ slidingウィンドウであるが、実際には61回/分で継続的な429エラーが発生し、キャッシュヒットのみが許可される。このスイッチをオフにした後、問題は解決した。したがってクライアント側は2秒間隔を維持し（ピーク時30回/分）、上流に十分な余裕を残す。

### 3.3 完全性ゲートとロールバック

訳後チェックは以下の3点を行う：

- [x] 各マーカーは正確に1回だけ出現する
- [x] スケルトンマーカーは行頭または行末に存在する
- [x] 返還後の構造のカウントは保存されている

いずれかのチェックに失敗するとリトライする。連続して失敗した場合、そのブロック**を2分木で再訳**し、それぞれが独立して復元可能な境界で分割する。フェンスやテーブルを分割しないようにする。通常の経路では追加のオーバーヘッドはゼロであり、失敗経路ではいくつかの呼び出しを追加して成功率を向上させる。

### 3.4 失敗の意味

パイプラインにおける失敗の定義は意図的に保守的である：**新しいファイルは書き込まない、古い訳文はその場で保持**。これは一般的な「部分的な成功でも提出する」とは矛盾しない。成功した部分は通常通り書き込まれ、失敗した言語は前のバージョンの内容を維持する。オンラインの読者には、構造が破損したページではなく、やや古い訳文が表示される。

3つの典型的な失敗経路：

1. モデルの出力が `max_tokens` 切り捨てられる → 予算を増やしてリトライ
2. 完全性ゲートによってブロックされる → ブロック全体をリトライし、それでも失敗すれば2分木で分割
3. 上流から429/5xxが返される → 指数バックオフまたは限界ウィンドウが満たされるまで待つ

2番目のタイプが最も詳しく説明する価値がある。あるブロックが20マーカーを含んでいると仮定し、モデルがその中の1ペア `**` を飲み込んだ場合、ゲートは「2つが欠けている」と報告する。リトライ時にモデルにマーカーを保持するようアラートし、それでも失敗すれば、そのブロックを行単位で2つに分割してそれぞれ別々に呼び出す。それぞれが約10マーカーとなり、原子を失う確率は大幅に低下する。実際のテストでは、典型的なロールバックは21行を1行 + 20行に分割し、その後2つの部分とも通過する。

### 3.5 キャッシュについて
ゲートウェイは7日間の応答キャッシュを提供しています。同じプロンプトを再送してもneuronを消費せず、上流には転送されません。これは**再実行**において特に役立ちます——ある実行が失敗した後、すでに成功したブロックの再要求はキャッシュにヒットするため、キャッシュにヒットしないブロックのみが再び課金されます。

しかし、キャッシュにより誤って判断されがちな現象もあります。上流またはゲートウェイがリミット状態に入った場合、キャッシュにヒットした要求のみが200を返却し、それ以外はすべて429になります。成功したログがあるからといってクォータが正常であると判断すると、完全に誤った結論を導き出すことになります。クォータが健全であるかどうかを判断するには、**非キャッシュ要求**の戻りコードを確認する必要があります。

関連する詳細情報として、キャッシュキーは完全なリクエストボディによって決定されるため、プロンプトバージョンの変更によりすべての履歴キャッシュが無効になります。これは、プロンプトをアップグレードした後、次のフルリトランスレートの費用が明らかに高くなる理由であり、障害ではなく予期された動作です。

### 3.6 フィールド呼び出しと本文呼び出し

2つの呼び出しの形態は異なるため、混同してはなりません：

|次元 | フィールド呼び出し | 本文呼び出し |
|---|---|---|
| 入力 | タイトル、要約、タグなどの短いテキスト | 分割された本文 |
| 出力制約 | JSON Schema 強制制約 | 純テキスト |
| 一般的な障害 | モデルがスキーマを拒否 | マークが失われたり切断されたり |
| リトライ戦略 | 純粋な解析に降格 | 二分法による降格 |

フィールド呼び出しに `response_format: json_schema` を使用した後、形式が不正な場合、API層でブロックされるため、追加の構造チェックはほぼ必要ありません。ただし、一部のモデルはこのパラメータを安定してサポートしていません。「JSON Mode が満たせない」というエラーが発生した場合、スクリプトは自動的に通常のJSON解析に降格し、今回のセッション内でこの言語を再度試行しなくなります。本文については逆で、MarkdownをJSONに詰め込むとモデルがリンク構文を破壊してしまうため、必ず純テキストを経由する必要があります。

## 4. 検証戦略

オフラインの自己テストでは、どのAPI呼び出しも消費せず、4つのアサーションをカバーします。

1.  全文語料の同一性往復：保護と復元が逆操作であることを保証
2.  パートごとの同一性往復：ブロックを分割しても空行構造は変化しない
3.  老朽化した事故の等価攻撃：マークが削除、重複、シフト、オーバーフローされた場合、門は必ずブロックする
4.  レート予算：2つの中長文の呼び出し数とピークレートの上限
レンダリング層では、三語 HTML の `table`、`tr`、`td`、`ol`、`ul`、`li`、`pre`、`code`、`del`、`sup`、`input` のカウントを比較する必要があります。構造が完全に一致していることを確認するためです。ビルドに成功したからといって、ページが正しいとは限りません。

### 4.1 ビルド時の検証

翻訳文を git に書き戻す前に、CI はまず `hugo --gc --minify` を実行します。このステップの目的は翻訳の品質をチェックすることではなく、** 誤った front matter ** をブロックすることです。TOML でクォートを一つ忘れたり、配列の括弧が対になっていなかったりすると、全体のサイトのビルドが失敗します。このチェックを提出前に設けることで、デプロイに失敗する内容をリポジトリに書き込まないようにできます。

`aliases` という点は見落とされがちです。多言語モードでは古いパスに言語プレフィックスを含めることはできません。Hugo は自動的に言語に応じて配置します。手動でプレフィックスをつけると、誤ったリダイレクトページが生成されてしまいます。このようなルールは、ドキュメントに記載して人に読んでもらうよりも、オフラインでのアサーションに組み込み、スクリプトが常にチェックできるようにしたほうが良いです。

### 4.2 テーマアップグレードの結合ポイント

テーマは submodule の形で導入されており、毎週上流の更新があります。サイト層では必要なみすじのテンプレートのみをカバーし、それ以外の機能は front matter のフィールドや拡張ポイントを通じて表現しようとします。カバーする部分が多いほど、毎週 PR をマージする際に衝突する確率が高くなります。

したがって、結合ポイントのリストが必要です。どのセレクタ、どのフック、どの partial 名がサイト層に依存しているのかを明確にします。毎回アップグレードの前後でアサーションを実行し、失敗した場合は直接 DOM スナップショットを表示することで、どの上流の変更が仮定に影響したのかを特定しやすくなります。このリストは本質的に ** 実行可能なインターフェース契約 ** であり、コメントよりも信頼性が高いです。

## 5. 責任の境界
| レイヤー | 責任 | してはいけないこと  |
|---|---|---|
| コンテンツ管理 | 通常のMarkdownを入力 | ビジネスロジックを扱わない  |
| サイトテンプレート | レンダリングと拡張ポイント | 上流のテーマの本体を変更しない  |
| 翻訳スクリプト | 構造の正確な保持 | 翻訳の良し悪しを判断しない  |
| CI | トリガーと書き戻し | 実行状態をポーリングしない  |

機能ロジックを**安定していてすべてを表現できる**レイヤーに配置することは、この設計において最も再利用価値のある原則です。トピックは毎週更新され、テンプレートがカバーする範囲が広くなるほど、マージコンフリクトが頻繁になります。したがって、front matterフィールドで表現できるものは、テンプレートを上書きしないでください。

## 6. まとめ

-  可靠性は「モデルが文法に触れられない」ことからではなく、「モデルが従う」ことから来ています
-  失敗した場合、古いコンテンツはその場に残され、オンライン上では損傷したページが表示されることはありません
-  プロンプトは極めてシンプルに保ち、複雑なルールはすべてプログラムに下げる
-  各構造の変更にはオフラインでのアサーションが備わっている必要があります
