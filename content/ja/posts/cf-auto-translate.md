> 本記事はAIによる自動翻訳です。表現が不自然な場合は[中国語の原文](/zh/posts/cf-auto-translate/)をご参照ください。

このブログは3ヶ国語（簡体字中国語 / 日本語 / English）で構成されています。中国語を書き終えて push すれば、日本語版と英語版が数分以内に自動生成・自動デプロイされます。その過程に人の手による翻訳作業は一切ありません。この記事では、その仕組みと、構築の過程でハマったポイントについて、分かりやすく解説します。

## 一、全体の概要

パイプライン全体が GitHub Actions 上で動作しており、すべて無料のリソースを使用しています。

```
写完中文文章 push
  → GitHub Actions 触发翻译
    → 调 Cloudflare Workers AI（免费额度）
    → 译文先过几道自动检查
    → 检查通过，机器人提交回仓库
      → Netlify 自动部署，日/英文版上线
```

実装に取り掛かる前に4つのルールを決めましたが、後になってそのすべてが非常に重要だったことが分かりました。

- **翻訳結果を git に取り込む**。日本語版と英語版はリポジトリ内の実ファイルとして存在するため、いつでも閲覧、修正、ロールバックが可能です。AIはあくまで「初稿の作成者」であり、直接公開する経路ではありません。
- **閲覧側は完全に静的**。APIキーは GitHub Actions 内にのみ存在し、ウェブサイト上にはキーもサードパーティ製のスクリプトも一切ありません。読者が私のために余計な電力を消費することはありません。
- **すべての呼び出しに明細を付ける**。すべてのリクエストは AI Gateway を経由するため、消費したトークン量、コスト、所要時間などがすべて記録されます。
- **一部の失敗が全体に影響しない**。日本語の翻訳が成功して英語が失敗した場合は、日本語版を先に公開し、英語版は旧版のままにして再試行を待ちます。

## 二、核心的な課題：AI は Markdown をめちゃくちゃにしてしまう

AI に純粋なテキストを翻訳させるのであれば、結果は非常に良好です。しかし、ブログ記事は単なるテキストではありません。リンク、コードブロック、テーブル、リスト記号などが混在しています。初期の頃は Markdown 全体をそのままモデルに投げ込んでいましたが、出力されたものは「見た目は合っているようで、実際には壊れている」ことがよくありました。実際の事例は以下の通りです。

```
原文：1. *感谢 [Hugo](https://gohugo.io) 提供代码支持*
翻后：[1. *Hugo](https://gohugo.io)に…（列表标记和星号被吞进了链接文字）
```
最も厄介なのは、この種の損傷**がエラーを出さない**ことです。リンクはそのままですし、ページも正常にレンダリングされるため、注意深く見ないと全く気づけません。プロンプトに「フォーマットを維持してください」と書くだけでは、実測では役に立ちませんでした。モデルは構文が見えてしまうと、どうしても構文をいじりたくなってしまうのです。

最終的に採用した方法は非常にシンプルです。それは**AIに構文を見せない**ということでした。

翻訳の前に、プログラムがまず記事を「分解」します。コードブロック、リンクのアドレス、インラインコード、各種マークアップ記号をすべて«0» «1»のような番号付きのプレースホルダーに置き換えます。AIが見るのは純粋な中国語の文章といくつかの番号だけなので、構文を壊そうとしても手出しができません。翻訳が終わった後、プログラムがプレースホルダーを元の状態にそのまま戻します。

分解には正規表現による強引なマッチングではなく、Markdownパーサー（remark）を使用して構文木に基づいて位置を特定しています。パーサーはすべての標準的な構文を認識しているため、将来新しい構文が登場してもパッチを当てる必要はありません。翻訳後には、いくつかの自動チェックが行われます。

1. **番号の整合性**：各プレースホルダーが正確に一度ずつ戻っていること。不足、過剰、重複はすべて失敗とみなされます。
2. **位置チェック**：リストのマーカーは行頭に、閉じ記号は行末に必ず存在していること。
3. **構造比較**：訳文と原文のリンク数、見出し数、テーブル数が一致していること。

チェックに通らない場合は自動的にリトライします。それでもダメな場合は、そのセクションを細かく分割して再翻訳します。さらにそれでもダメな場合は、その行をそのまま残します。一文が翻訳されなくても、記事全体が壊れてしまうよりはマシだからです。

## 三、コスト削減メカニズム：変更された分だけを翻訳する

各翻訳ファイルには2つの「指紋」（ハッシュ）が付いています。一つは本文に対応し、もう一つはタイトルや要約などのフィールドに対応しています。

```toml
source_hash = '…'        # 正文的指纹
source_fields_hash = '…' # 字段的指纹
```

翻訳の前に、まず指紋を比較します。
- で**本文**を変更しました → 本文のみを再翻訳し、タイトルと要約は以前のものをそのまま使用します。
- は**の要約またはタグ**のみを変更しました。→ フィールドのみを再翻訳し、本文の費用は一切かかりません。
-  何も変わりません → 呼び出しゼロ（毎週日曜日の深夜に行われる定期的な照合も、このようにフルスキャンを行うだけで、差異がなければ費用は一切かかりません）

また、CloudflareのAI Gatewayには7日間のキャッシュ機能が備わっています。同じリクエストを再度送った場合は前回の回答がそのまま返されるため、料金は発生しません。そのため、誤字を一つ修正して反映させたとしても、多くの場合、実際に変更された部分の費用だけで済みます。

実測値：無料プランは1日あたり10,000 neurons（Cloudflareの計算リソースの課金単位）で、3,000文字の記事を1言語に翻訳するのに約50〜160 neuronsを消費します。——1日に十数本翻訳しても使い切ることはありません。

## 四、中国語の要旨もそれが担当しています。

文章を書き終えた際、要約を記入し忘れてしまうことがあります。パイプラインが中国語の記事に `description` がないことを検知すると、本文の内容に基づいた70〜160文字程度の要約を自動的に作成し、記事ファイルに書き戻します。3言語の要約はすべてこの文章を元に翻訳されます。——**3言語の要約は常に同じ内容になります**。その後、CMSで要約を手動で修正して保存すると、3言語すべてが自動的に更新されます。

## 五、人は常に一票を持っています。
自動化が最も陥りやすい失敗は、「機械が完全に自動化され、人間が介入できなくなること」です。このワークフローは、人間が介入するための完全な経路を確保しています。

- CMS内で特定の訳文に**「訳文をロック」**をチェックする：これにより、その訳文は以後、手動で作成された原稿として扱われ、上書きや削除が行われなくなります。また、中国語の原文が更新されても同期されません。
- CMS内で中国語の記事に**「翻訳しない」**をチェックする：その記事はワークフローから除外されます。
- 校閲済みの機械翻訳が、無計画に再翻訳されることはありません。中国語の原文の該当箇所に変更がなければ、フィンガープリントが変わらないため、再翻訳のコストが発生しません。
- ライフサイクルの自動同期：中国語の記事が削除されれば訳文も削除され、中国語の記事が下書き状態になれば訳文も公開停止となります。

## 六、陥りやすい罠（もし同様の仕組みを構築したい場合）

多額の費用（と時間）をかけて得た、いくつかの教訓：

- **レート制限には、能動的に適応する必要があります**。Cloudflareのレート制限はドキュメントに記載されているよりも発生しやすいため、事後に対処（バックオフ）するよりも、クライアント側でリクエスト速度を一定に落としておく（2秒に1回など）方がずっと手間がかかりません。
- **AIに本文をJSON形式で出力させないでください**。MarkdownをJSONに詰め込むと、モデルによってバラバラに分解されてしまうため、本文は必ずプレーンテキストにする必要があります。
- **失敗したときは、保守的であることを優先してください**。訳文に疑いがある場合は公開せず、旧バージョンをそのまま残して次回の再試行を待ちます。静的ブログにおいて「古い」ことは、「壊れている」ことほど致命的ではありません。
- **すべての防衛線において、オフラインでの自己テストを行ってください**。このシステムのチェックロジックには数十ものアサーションがあり、変更のたびに実行してもAPIの消費はゼロです。
