> 本記事はAIによる自動翻訳です。表現が不自然な場合は[中国語の原文](/zh/posts/cf-auto-translate/)をご参照ください。

このブログは3か国語（簡体中国語／日本語／英語）で書かれています。私は中国語を書いた後、それをプッシュすると、日本語版と英語版は数分で自動生成され、自動的にデプロイされます――中間には一切の人工翻訳の工程がありません。この記事では、それがどのように動作するのか、そしてその過程で踏んだミスについて、わかりやすく説明します。

##  一、全体の構造

このフローはGitHub Actions上で動作しており、すべて無料リソースを使用しています。

```
写完中文文章 push
  → GitHub Actions 触发翻译
    → 调 Cloudflare Workers AI（免费额度）
    → 译文先过几道自动检查
    → 检查通过，机器人提交回仓库
      → Netlify 自动部署，日/英文版上线
```

始める前に4つのルールを決めました。その後、それぞれが命を救ってくれました。

- **翻訳はgitに反映**。日本語版と英語版はリポジトリ内の実際のファイルであり、いつでも開けたり、編集したり、ロールバックしたりできます。AIは「初稿の作成者」であり、配信経路ではありません
- **訪問者側は完全に静的**。APIキーはGitHub Actions内にのみ存在し、ウェブページ上にはキーも第三者スクリプトもありません。読者の方は私のために一度も電力を使用しません
- **毎回の呼び出しには明細があります**。すべてのリクエストはAIゲートウェイを経由し、どのくらいtokenを使ったか、いくらかかったか、どのくらい時間がかかったか、すべて記録されています
- **一部の失敗が全体に影響しない**。日本語の翻訳は成功したが、英語の翻訳が失敗した場合、日本語は先に公開され、英語は古いバージョンのまま待機して再試行を待ちます

##  二、コアの問題：AIはMarkdownを壊す

AIに純粋なテキストを翻訳させると、効果はすでに良いです。しかし、ブログ記事は純粋なテキストではありません――リンク、コードブロック、テーブル、リストの記号が混ざっています。初期には、全体のMarkdownをモデルに投げていたため、翻訳された結果は「正しいように見える」ものの、実際には破損していました。実際の事例： 

```
原文：1. *感谢 [Hugo](https://gohugo.io) 提供代码支持*
翻后：[1. *Hugo](https://gohugo.io)に…（列表标记和星号被吞进了链接文字）
```
最も厄介なのは、このような損傷**はエラーを出さない**——リンクは同じリンクのまま、ページは同じようにレンダリングされるので、よく見ないと気づかない。プロンプトに「フォーマットを保持してください」と書いても、実際には効果がない。モデルは文法が見えると、どうしても文法を変えたがる。

最終的に使った方法はとても単純だった：**AIに文法を見せない**。

翻訳する前に、プログラムが文章を「分割」する。コードブロック、リンクアドレス、インラインコード、さまざまなマーカー記号はすべて«0»«1»のような番号のプレースホルダーに置き換えられる。AIが見るものは純粋な中国語の文といくつかの番号だけなので、文法を破壊しようとしてもできない。翻訳が終わったら、プログラムがプレースホルダーを元のまま戻す。

分割にはMarkdownパーサー（remark）を使用し、構文木を使って位置を特定している——正規表現で強引にマッチさせるのではなく、パーサーはすべての規範的な構文を認識しているので、今後新しい構文が出てきてもパッチを当てなくてもよい。翻訳後にはいくつかの自動チェックがある。

1. **番号の完全性**：すべてのプレースホルダーが正確に一度戻ってこなければならない。少なくとも、多くて、重複していると失敗とみなされる。
2. **位置チェック**：リストのマーカーは行頭に、終了記号は行末になければならない。
3. **構造比較**：翻訳文と原文のリンク数、見出し数、表の数は一致している必要がある。

チェックに通らなければ自動的に再試行する。それでもだめなら、そのセグメントを小さく分割して再翻訳する。それでもだめなら、一行ずつ元のまま残す——一行も翻訳しないほうが、全体が壊れているよりましだ。

## 三、コスト削減メカニズム：変更した分だけ翻訳する

各翻訳ファイルには2つの「指紋」（ハッシュ）が含まれており、一つは本文に対応し、もう一つは見出しや要約などのフィールドに対応している：

```toml
source_hash = '…'        # 正文的指纹
source_fields_hash = '…' # 字段的指纹
```
- 変更しました**本文** → 本文のみ再翻訳、タイトルや要約は古いものを使用します
- のみ**要約またはタグ**を変更しました → フィールドのみ再翻訳、本文は変更しません
- 何も変わりません → 0回呼び出し（毎日日曜日の定時精算ではこのように全量スキャンを行っており、クリーンな状態では一切費用がかかりません）

また、Cloudflare の AI Gateway には 7 日間のキャッシュが標準で付いています。同じリクエストを2回目に出すと、すぐに前の答えを返すため、料金はかかりません。そのため、誤字を修正してアップロードしても、実際に変更した部分だけの費用で済みます。

実際の数値：無料プランでは1日あたり10,000ニューロン（Cloudflare の計算力の単位）が使用可能で、3,000字の記事を1言語に翻訳するには約50〜160ニューロン程度かかります。1日で10篇以上翻訳しても使い切れません。

## 四、中国語の要約もこれに含まれます

記事を書いた後に要約を忘れてしまうことがあります。ラインが中国語の記事に`description`がないことを検出すると、自動的に本文の内容に基づいて70〜160字の要約を生成し、記事ファイルに戻します。3言語の要約はすべてこの内容を元に翻訳されています――**3言語の要約は常に同じことを述べています**。その後、CMSで手動で要約を編集して保存すると、3言語の要約も自動的に更新されます。

## 五、人は常に一票を持っています

自動化が最も誤って進みやすい方向は「機械が完全に自動で、人が介入できない」というものです。このラインでは、人間が完全に取り組める道を残しています：

- CMSで特定の翻訳に「翻訳をロック」をチェック：この翻訳は以降、人間の原稿として扱われ、上書きや削除はされず、中国語の原文が更新されても同期されません
- CMSで中国語の記事に「翻訳しない」をチェック：この記事は即座にラインから除外されます
- 校正済みの機械翻訳は無闇に再翻訳されません：中国語の原文の対応部分が変更されていない限り、フィンガープリントは変化せず、再翻訳に費用はかかりません
- ライフサイクルが自動で同期されます：中国語の記事が削除されると、翻訳も一緒にクリーンアップされます。中国語の記事が下書きに変更されると、翻訳も一緒に下架されます

## 六、踏んだ穴（あなたもこれを構築したい場合）

いくつかの本物のお金（と時間）で得た教訓があります：

- **レートリミットは積極的に対応する必要があります**。Cloudflare のリミットはドキュメントに記載されているよりも簡単に発生します。クライアント側でリクエスト速度を一定に保つ（2秒に1回）ことは、後からリトライするよりも効率的です。
- **AI に JSON 形式で本文を出力させないでください**。Markdown を JSON に詰め込むと、モデルによってバラバラにされてしまいます。本文は純粋なテキストでなければなりません。

- **失敗したときは保守的であってもかまいません**。翻訳の結果に疑問がある場合は公開せず、古いバージョンをそのままにしておき、次回の再試行を待ちます。静的ブログの「古い」ことは「悪い」ほど致命的ではありません。

- **すべての防御ラインにはオフラインでの自己テストが必要です**。このシステムのチェックロジックには数十のアサーションがあります。たとえ小さな変更でも、毎回実行し、API の使用はゼロにしています。
