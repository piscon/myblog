## 一、すべて緑色ですが、リンクが切れています

公開して3日目、偶然記事の下部にある**「GitHubでこの記事を改善する」**をクリックしてみたところ、404エラーになりました。ついでに他の2記事もクリックしてみましたが、同様でした。

奇妙なのは以下の通りです：

| チェック查 | 結果 |
|---|---|
| ローカル `hugo --gc --minify` | ✅ |
| CI build-check | ✅ |
| feature-check 26 项 | ✅ |
| Netlify デプロイ日志 | ✅ すべて緑色 |
| あのリン接 | **404** |

> すべての自動チェックは「ページが生成できるか」を検証しており、「生成されたURLが正しいか」を検証しているものは一つもありませんでした。

## 二、一行の main

サイト層の `editPost` 設定は以下のようになっています（簡略化）：

```toml
[params.editPost]
  URL = "https://github.com/piscon/myblog/blob/master"
  appendFilePath = true
```

問題が発生したバージョンでは、その `master` が **`main`** と書かれていました。リポジトリのデフォルトブランチは常に `master` なので、GitHub 上に `blob/main/...` が存在しないのは当然です。

** 間違っているのは文字列の一文字であり、ロジックではありません。** Hugo はこの URL を検証せず、テンプレートは文字列を結合するだけなので、ビルドは当然すべて緑色になります。

- [x]  結合されたパスの形式は正しい
- [x]  ファイルは存在する
- [ ] **ブランチ名が誰も確認していません**
- [ ] 成果物のリンクも誰もクリックしていません

*設定を書く際、おそらく手慣れている方の単語をそのまま打ち込んでしまいました。*

## 三、なぜ検知できなかったのか

振り返る際に最も気になるのは、「書き間違えたこと」ではなく、「なぜこれほど静かに間違っていたのか」ということです。

1. **それは純粋なデータ**であり、コードではないため、静的解析では手が付けられません
2. **feature-checkがアサートしているのはDOM構造**（`a.edit`があるか、classが正しいかなど）であり、外部ドメインのURLは対象外です
3. ローカルでクリックしましたか？**いいえ**。開発中はレイアウトの確認ばかりしていました
4. Netlifyはビルドを行うだけで、リンク先がどこであるかは関知しません

| 层 | 検知可能か吗 | 原因 |
|---|---|---|
| Hugoテンプレート板 | 不能 | 文字列の結合のみを行うため |
| ビルド時チェック验 | 不能 | URLを解析しないため |
| feature-checkk | 不能 | セレクターをアサートするもので、外部リンクはアサートしないため |
| 手動でのクリック一下 | **可能** | ただし、3日後になってからクリックするため |
> のようなバグの正式名称は、おそらく「**誰も責任を取らないあの枠**」といったところでしょう。

## 四、補填したあの枠

修正自体は一瞬です。「`master`」に戻すだけですから。しかし、防御線を張るのには少し気を遣いました。

`feature-check.sh`にアサーションを追加しました。ビルド成果物内の編集リンクを直接 grep し、「**ブランチセグメントがリポジトリのデフォルトブランチ**と一致すること」を検証します。

```bash
check "editPost 分支与默认分支一致" \
  "grep -q '/blob/$(git symbolic-ref --short refs/remotes/origin/HEAD | sed 's|origin/||')/' '$PAGE'"
```

さらに、「`hugo.toml`」の横にコメントを一行追加しました。

```toml
# 分支必须与仓库默认分支一致（master）——曾误写 main 致全站死链
```

| 法 の補填 | 防ぐ内容 |
|---|---|
| ブランチ段 のアサーション | 今後また書き間違えた際、CIを即座に落とす |
| 設定への注釈释  | 人が修正する前に気づけるようにする |
| 文書への振り返り档  | 次回から「ついでにポチッと」で済ませないようにする |

- [x]  masterに戻す
- [x]  アサーションを追加（現在27項目）
- [x]  注釈を追加
- [ ]  ついでに他のハードコードされたドメインも一通り確認（TODOとして記録）

##  五、バグ修正よりも残しておく価値があるもの
今回を境に、ある習慣を改めました: ** ビルドが通っただけで終わらせず、ついでに成果物のリンクを一つクリックしておく** ことです。コストはわずか3秒ですが、これで「データは間違っているがフォーマットは正しい」という落とし穴をすべてカバーできます。

もう一つ、より一般的な結論があります: ** 自動チェックは構造の検証には長けていますが、事実の検証には向いていません**。構造が間違っていればエラーで止まりますが、事実（ブランチ名、ドメイン、日付、IDなど）が間違っていると、静かに、そして長い間間違ったまま進んでしまいます。ですから、アサーションには、たとえ文字列をgrepする程度であっても、できるだけ「事実型」のものをいくつか混ぜておくべきです。

>  あの一行のコメントは、今も設定ファイルの中に残っています。それは実行されるものではありませんが、誰かがそのURLを変更しようとするたびに、「かつてmainを誤って書き込み、サイト全体をデッドリンクにした」という教訓が目に飛び込んできます。

** コードは振る舞いを管理し、コメントは記憶を管理します。** 今回は、その両方を使いました。
