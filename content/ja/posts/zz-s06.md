## 一、8秒は遅いわけではないが、何かがおかしい

記事数は30件に満たないのに、`hugo --gc --minify` ローカルでの実行に8秒以上かかっています。絶対的な数値としては驚くほどではありませんが、** 同じリポジトリでも先週までは2秒** でした。その間に機能を追加したのは、せいぜい2、3個です。

>  動作が遅くなること自体は怖くありません。恐ろしいのは、どのバージョンから遅くなったのかが分からないことです。

まずは最も愚直な方法をとります。`git log` 直近の10個のコミットを確認し、一つずつ checkout してビルド時間を計測します。

| コミット交 | ビルド建 | 怪しい点 |

| 検索機能の追加重 | 2.2s | 無関係 |
| アーカイブページのローカル化 | **7.9s** | ✓ これだ |

## 三、あのコードの行

アーカイブページを年月ごとにグループ化する場合、元の書き方は大体こんな感じでした：

```go
{{ range .Site.RegularPages }}
  {{ $y := .Date.Format "2006" }}
  {{ $posts := where (where .Site.RegularPages "Section" "posts") "Date" ">" ... }}
  {{ range $posts }}…{{ end }}
{{ end }}
```

外側の`range`がN件あると、内側の`where`はサイト全体のページに対して**N回もフィルタリングをかけている**ことになります。記事が少ないときは分かりませんが、多言語化でページ数が3倍になると、一気に複雑さが浮き彫りになります。
改善の仕方が全くスマートではありませんでした。フィルタリングの**をループの外に出して、**を一度だけ行うようにすべきでした。

```go
{{ $all := where .Site.RegularPages "Section" "posts" }}
{{ $groups := $all.GroupByDate "2006-01" }}
{{ range $groups }}…{{ end }}
```

`GroupByDate` は Hugo に標準で備わっているもので、今まで使うことを思いつきませんでした。

## 五、なぜ記録しておく価値があるのか

最初の3つの試行がすべて間違いだったからです。しかも、どれも「正解っぽく」見えました。キャッシュのクリア、パラメータの削除、テンプレートの簡素化——どれも理にかなっており、すべてテストしましたが、どれも効果はありませんでした。

本当に効果があったのは、**推測する前にまず計測する**ことでした。各コミットのビルド時間を表にまとめると、遅いバージョンが自然と浮き彫りになりました。もし経験だけで画像の最適化を行っていたら、おそらく今頃も、全く変わっていない画像に対して WebP 変換を繰り返していたことでしょう。

- **まず特定し、それから手を動かす**
- 計測していないものは最適化しないこと
- フレームワークの標準関数をまず調べ、自分でループを書かないこと
- ~~8秒なら我慢できます~~ 我慢できません
